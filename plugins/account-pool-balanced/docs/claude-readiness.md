# Claude client readiness

When Claude routing is enabled, managed Claude launches retain the pool URL and scoped token even if no account is currently usable. Temporary account unavailability therefore produces a pool refusal rather than silently dropping pool configuration and exposing local authentication as the next path. Explicit routing-off and intentional thread bypass retain their existing behavior. This does not control independently launched applications outside BB.

The bounded request journal may record a clientVersion extracted from a short Claude CLI user-agent. This field is self-reported and must never authorize a request or stand in for trusted machine identity. Caller binding remains the authenticated context and its existing client hash. Unknown, oversized or malformed versions become null. Raw user-agent strings, device identifiers, headers, prompts and credentials are not persisted by this feature. Old retained rows without the additive field remain valid. Existing journal retention, row/byte limits and error isolation are unchanged.

A host readiness audit should resolve the actual executable, record its version and run the shell doctor command with a finite deadline, without automatically applying suggested repairs or launching model prompts. Record warnings separately from the process exit code: a successful exit can still report duplicate installations. Keep full diagnostic output private on that host. Offline hosts remain unverified; absence from the available-host snapshot is not a successful audit. A successful doctor check is an installation diagnostic, not proof of account authorization, safe traffic volume or immunity from provider enforcement.

Align managed client versions through supported installation tooling after reviewing active use. Never merge machine identifiers or copy authentication directories to make machines appear identical. The existing two-request account cap and provider cooldowns remain in force. Additional request pacing and periodic host checks are separate follow-up work; this release does not add them or promise zero upstream errors.


## Shared start spacing

`claudeRequestStartIntervalMs` is a local preventive interval between Claude inference starts for each selected account, shared by native and external callers on all hosts. It is separate from the concurrent-stream cap. It defaults to `0` on old and new installations for compatibility; an operator can explicitly enable it through `bb pool config set claudeRequestStartIntervalMs 1000`. This example is an operational pacing choice, **not** a published provider limit or a guarantee against rejection. Integers from 0 to 60000 are accepted. Other providers keep their existing behavior.

Admission waits for both this interval and the actual provider hold. Starts are rechecked and timestamped under the final account snapshot, after asynchronous network checks: two waiting requests cannot restart together when a hold ends. Existing account/purpose eligibility, request deadline, cancellation and stream lifetime remain in force. Changing the interval wakes current waiters but never clears a provider hold. Running streams are not timed out by start spacing. Start timestamps are in-memory; provider holds retain their existing persistence.

## Scheduled installation checks

`scripts/claude-host-doctor.py` supports a local read-only check (`--local`) or checks through existing authenticated BB machine terminals. The latter requires an explicit operator-owned JSON list of 1–8 existing machine IDs (`--hosts-file`) and a private `--state-dir`; it does not discover/enroll new hosts or change permissions. Offline and unknown hosts are recorded as unverified without waking them. The trusted target is the native terminal's host identity, not a field supplied by the diagnostic payload.

Each connected target runs only `claude --version` and `claude doctor`, with finite timeouts and per-child auto-update disabled. No model, login, installer or settings mutation is invoked. A zero exit alone does not prove readiness: the diagnostic must positively report no installation issues and no duplicate/settings warning. Only a strict version, exit code and fixed issue categories are retained; raw diagnostic output, arbitrary strings, credentials and configuration contents are not exported. Each host has one latest receipt with its check time. Changed results are printed for the existing script-automation history; unchanged checks stay silent. An operator can schedule the script daily using the existing BB script automation, without model workers or new services. It does not alter existing automation holds.

This verifies installation health, not account standing or permission to use an account. Offline hosts remain unverified. Independent applications outside managed pool routing and their sessions are outside this control.
